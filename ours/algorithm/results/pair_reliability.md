# Two-motion commands: reliability test before the pilot

Generated by `algorithm/scripts/pair_reliability.py`: the live app's chain (detector with quiet x3 -> head frame -> features -> Rules or Model from `live_model.json` -> pair decoder) run in Python.

**Summary.** (1) Two motions done back to back without a pause merge into ONE detected event (real doubles of 4 people: 84-89 % merged), so the command is lost. The detector needs ~0.4 s of stillness to end a motion. (2) With a pause of 0.5 s or more between the two motions, the full chain gets about 9 in 10 commands right on P01's motions (most failures involve circles). (3) Naming on NEW people is not shown by this test: only the live test (or the pilot) can show it.

**Naming check.** Even when merged, a double tilt-left is still a tilt whose first swing goes left, so 'at least one right' should be high; it is not. Flipping the nod sign (as if these people nodded chin UP first) does not fix it either, so it is not only the calibration sign:

| double        |   rules_at_least_one, sign flipped |
|:--------------|-----------------------------------:|
| nod_2x_front  |                               0.06 |
| tilt_2x_left  |                               0.13 |
| tilt_2x_right |                               0.29 |

Whole-person head-frame shares on this data are right (tilts load on the tilt axis), so the per-event naming of these old cut takes fails for reasons not pinned down here (merged double motions mix axes and swings; 2.5 s takes often start mid-motion, so the head posture before an event is unknown). Treat part A as evidence about MERGING only, not about naming.
